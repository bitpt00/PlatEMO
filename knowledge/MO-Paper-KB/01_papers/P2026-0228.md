# Autonomous Multiobjective Optimization Using Large Language Model

## 一句话理解

本文提出 LLMMOP，用 LLM 自动生成、测试、修复和进化 MOEA 的 `Reproduction` 代码，把算法设计从人工调算子转为“文本程序种群”的迭代搜索。

## 问题与动机

- 研究问题和场景：真实 MOP 类型多样，连续变量、二进制组合、排列组合等编码差异很大；传统 MOEA 的 reproduction operator 和超参数往往需要专家按问题手工设计。
- 现有算法为什么不足：
  - 人工设计 MOEA 需要大量领域与算法经验，普通用户难以为 unseen MOP 快速配置有效搜索算子；
  - 现有 LLM-assisted program evolution 多用于数学发现、TSP/组合启发式或单目标场景，还没有系统面向 MOEA reproduction design；
  - LLM 生成复杂代码常出现编译、运行时错误或死循环，直接丢弃会浪费可能有创意的设计；
  - 传统固定父代数量的进化搜索不适合文本代码提示，容易让 LLM 反复生成相似程序。
- 本文希望解决什么：让 LLM 自动设计 MOEA 中的 `Reproduction` 方法，并通过 pilot run、error-driven repair、dynamic parent selection、prompt-based crossover/mutation 提高生成代码的可执行性、创新性和跨问题表现。

## 核心理念与算法流程

- 核心理念：把 MOEA 的 reproduction function 当作可以进化的程序个体。LLM 负责根据任务描述、父代代码和错误信息生成或修改代码；程序个体通过在 MOP validation set 上运行获得分数；可执行性由独立进程 pilot run 和 repair 对话保证。
- 主要流程：
  1. 用户提供 `#PROBLEM#`、`#PROBLEM_DESC#`、`#FORMAT#` 等任务提示，LLM 生成初始 `Reproduction` 方法种群。
  2. 每个生成方法先进入 Pilot Run and Repair：在 toy/validation problems 上限时运行，若有错误则把 error message 加入 repair prompt，让 LLM 修复。
  3. 可执行方法在多个 validation MOP 上并行评价，计算 normalized score。
  4. 每代按分数为 reproduction methods 赋选择概率，并随机抽取 `Ns` 个父代，其中 `1 < Ns <= Nmax`。
  5. Crossover prompt 把 `Ns`、父代代码和任务要求喂给 LLM，生成新的 reproduction method。
  6. Mutation 以 `1/2` 概率让 LLM 对 crossover 代码做轻微修改，否则保留 crossover 结果。
  7. 新代码继续通过 Pilot Run and Repair、并行评价和 elitist update。
  8. 搜索结束后保留在 validation MOP 上分数最好的 reproduction methods，并在更大 testing MOP 上评估泛化。
- 关键组成部分：
  - Informative prompting：初始化、交叉、变异、修复分别有任务化 prompt。
  - Dynamic Reproduction Selection：父代数量和父代集合动态变化，增加 prompt 多样性。
  - Textual Crossover and Mutation：将代码片段和设计要求作为文本遗传材料。
  - Pilot Run and Repair：把编译/运行错误作为反馈，限时独立进程避免死循环。
  - Parallel evaluation and normalized score：跨多个 MOP 评价程序个体的稳定性能。
- 可能被修改的位置：
  - 可把 `Reproduction` 扩展为 initialization、environmental selection、repair、local search 或 parameter controller；
  - scoring 可替换为 HV、IGD、运行时间惩罚、可行率、稳定性或跨实例泛化指标；
  - repair prompt 可加入单元测试、静态分析、类型检查或 sandbox trace；
  - dynamic selection 可加入 novelty、code diversity、失败类型多样性或成本。
- 必须保留的核心：LLM 生成的算法代码必须经过可执行 pilot run 与错误驱动 repair，并用真实 MOP validation score 进入进化循环；只做一次性 prompt 生成不属于本文关键机制。

## 实验证据

- 测试问题和对比算法：
  - 连续 MOP：validation 使用 ZDT1-6、DTLZ1-7 默认规模；testing 使用更高维对应实例。
  - MOKP：validation 为 10 个随机生成实例，items 50-200；testing 为 20 个不同容量和 items 100-200 的实例。
  - MOTSP：validation 为 20 个 30-city 实例；testing 为 20 个 100-200 vertices、不同分布的实例。
  - 对比四个 hand-crafted MOEA：CTAEA、NSGA2、AGEMOEA、SMSEMOA；并与 SOTA LLM program search EOH 比较。
  - LLM 包括 `gpt-4-1106-preview`、`gpt-4o`、`Gemini-1.5-pro`、`Claude-3-opus`；temperature 0.5；program population `Nev=10`，fitness evaluation 100，pilot run `MaxT=2000s`，repair trials `Ntrial=2`。
- 主要实验结论：
  - Validation convergence shows：LLMMOP 和 EOH 都能通过迭代反馈提升 reproduction 方法；LLMMOP 初始化质量整体优于 EOH。
  - Testing CMOP：LLMMOP 得到最低 average IGD，尤其在 ZDT6、DTLZ1、DTLZ6 等较难任务上优于 EOH 和人工 MOEA。
  - Testing MOKP：LLMMOP 在多数 testing cases 上显著优于竞争方法，average HV 最好；作者分析其生成了有效 repair function，例如优先移除 heaviest item 来满足容量约束。
  - Testing MOTSP：LLMMOP 在不同顶点分布和规模上取得最好或最具竞争力泛化表现，优于 EOH 和手工 MOEA。
  - Efficiency：NSGA2 运行最快；LLMMOP 在 CMOP/MOKP 上效率有竞争力，但在 MOTSP 上约 841 s、为最慢，质量高但代价大。
- 消融或机制证据：
  - Informative prompt 对 MOKP 和 MOTSP 的初始 reproduction population 质量优于 concise prompt，MOTSP 上差异更明显。
  - Pilot Run and Repair：对 4 个 LLM 每个生成 20 个 reproduction methods，GPT4O/GEMINI 初始可执行率约 80%；GPT4 初始成功较低但 repair success rate 达 81.8%，说明 repair 能挽回大量错误代码。
  - Dynamic selection：带 dynamic selection 的 GPT4 版本在 CMOP validation scores 上持续提升；去掉 dynamic selection 后虽初始化不错但后续停滞。
  - 不同 LLM 对比显示 LLMMOP 对多种商业 LLM 都有效，Claude 生成的最佳 reproduction 包含更复杂 hybrid selection、adaptive crossover/mutation 等设计。
- 证据边界：
  - 仅做 3 次 LLM program-search 独立运行，LLM 响应随机性和商业模型版本差异会影响可复现性；
  - 详细 best reproduction code 在 supplementary，主文只概述部分策略；
  - 大量结果表在 Markdown 中为图片占位，需 PDF/补充材料补精确数值；
  - 该框架搜索成本高，适合离线算法设计，不适合每个新实例在线即时调参。

## 局限与未来工作

- 作者明确说明的局限：
  - 黑箱连续优化问题中问题信息有限，LLM 早期生成的 reproduction 方法质量较低；
  - MOTSP 上 LLMMOP 得到的 reproduction 方法运行时间最长，显示代码质量/复杂度与求解质量存在折中；
  - LLM 生成算法含多个参数，性能受生成细节和模型能力影响。
- 作者未来工作：
  - 将专家知识与 LLMMOP 结合，提高黑箱优化问题的搜索效率；
  - 探索不同 LLM 的能力，以提升生成算法质量和一致性。
- 我们认为仍需确认的问题：
  - 如何隔离 LLM 模型能力、prompt 设计、evolution loop 和 repair 模块的独立贡献；
  - 自动生成 reproduction 是否在更多约束、动态、大规模、many-objective 和昂贵评价 MOP 中泛化；
  - 如何加入代码复杂度、运行时间和可维护性惩罚；
  - 商业 LLM 更新后结果是否稳定复现。

## 可复用知识与创新线索

- 值得建立或补充的设计知识：建立“可执行测试修复的 LLM 算法代码进化”，因为它给出一种可迁移到算子、启发式、修复器和选择策略自动设计的闭环。
- 暂留在论文卡中的方法、原理或架构启发：
  - 错误不是只用于过滤，也可作为 informative feedback 驱动 LLM 修复和探索；
  - 文本交叉的父代数量不必固定，动态改变父代数量能显著增加 prompt 多样性；
  - validation set 应小规模、能快速评价；testing set 应更大规模，用来检验泛化。
- 局部创新线索：
  - 用 LLM 自动生成约束修复器、局部搜索算子或变异算子，再接入现有 MOEA；
  - 在 score 中加入 runtime penalty，避免 LLMMOP 找到质量高但过慢的 MOTSP reproduction；
  - 把 static analysis 和 unit tests 加入 Pilot Run，提高 repair 可定位性。
- 结构创新线索：
  - 构建“LLM 生成程序 -> sandbox 测试 -> 错误修复 -> 小实例评分 -> 文本交叉变异 -> 大实例验证”的算法工厂；
  - 为不同问题族维护 reproduction program archive，让新问题从相近代码种群 warm start。
